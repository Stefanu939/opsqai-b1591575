# OPSQAI — Complete Product Audit (2026-08-10)

Audit only. No source code, schema, API, RBAC, AI or installer logic was modified.
Method: full static read of all 47 authenticated route files + shared shells, server
functions, migrations, plus read-only DB introspection of licence constraints/indexes.

Product areas:
1. Management Center — `src/routes/_authenticated/management*.tsx`, `src/components/mc/*`, `src/lib/{licenses,releases,companies,mc-admin,installation-package}.functions.ts`
2. Customer Portal — `src/routes/_authenticated/portal*.tsx`, `src/lib/{portal,portal-admin,support}.functions.ts`
3. Self-Hosted Application — `src/routes/_authenticated/app.*.tsx`, `src/components/app/*`, `src/lib/ai-*`, `src/lib/providers/*`

# REPORT 1 — MANAGEMENT CENTER

## Strengths
- Uniform IA and component vocabulary: `PageHeader`, `DataTable`, `SectionCard`, `StatCard` used on every page; `mc-shell.tsx` sidebar has active states, keyboard-navigable links, mobile drawer with backdrop.
- Authorization is systematic, not ad hoc: every server fn opens `.middleware([requireAuth])` then `await requirePlatformAdmin(context)` (licenses, releases, mc-admin, installation-package, activation).
- Zod validation on every mutation, with a shared strict `InstallIdSchema` regex (`src/lib/licenses.functions.ts:11-15`).
- Secret hygiene: `assertNoBlacklistedSecrets` before persisting admin-supplied JSON (`licenses.functions.ts:98,145,338`); ownership transfer deliberately never stores customer infra secrets.
- Good operational micro-UX: colour-coded expiry urgency (`management.customers.tsx:190-213`), relative heartbeat age + 30s polling on Installations (`management.installations.tsx:43-65`), no-op guard on ownership transfer (`licenses.functions.ts:348-350`).
- Every `DataTable` supplies a tailored `empty` state distinguishing "no data" from "no match".

## `duplicate key value violates unique constraint licenses_install_id_key` — root cause

Confirmed chain (code + live DB introspection):

1. `issueLicense` (`src/lib/licenses.functions.ts:93-136`) signs the token and then performs a **bare `insert`** into `licenses` with `kind:'install'` — no `SELECT … WHERE install_id = … AND kind='install'` pre-check, no upsert, no `onConflict`.
2. Its siblings do it correctly: `issueModuleLicense` (`:172-214`) checks-then-insert/update; `importLicenseToken` (`license-import.server.ts:109-146`) and the self-hosted mirror `upsertMirrorRow` (`local-licensing.server.ts:184-256`) both check-then-branch. So the correct pattern already exists and is simply not applied to install licences.
3. The UI actively invites the collision: `management.licenses.tsx:338-346` slugifies a company name into a suggested `install_id` (accent/punctuation stripping means "Acme, Inc." and "ACME Inc" both → `acme-inc`), and `pickCompany` (`:379-391`) pre-fills `install_id` from an **existing** company — i.e. the happy path for "re-issue for an existing customer" submits an `install_id` that already has an install row. No availability pre-check, no submit-disable de-dupe against double-click/two-tab races.
4. The raw Postgres message reaches the admin verbatim: `licenses.functions.ts:134` throws `error.message`, `management.licenses.tsx:105` renders `toast.error(e.message)`.
5. Constraint naming: `licenses_install_id_key` (plain `UNIQUE(install_id)`) was created in `supabase/migrations/20260708191748_*.sql:17` and **dropped** in `20260716164250_*.sql:5`, replaced by partial unique indexes. Live introspection confirms cloud now has `licenses_install_unique` / `licenses_one_install_per_id` (`UNIQUE(install_id) WHERE kind='install'`) and no `licenses_install_id_key`. Therefore the reported error text originates from either (a) a pre-`20260716164250` database, or (b) a self-hosted/older mirror install where the legacy constraint still exists (`migrations/selfhost/0011_license_mirror.sql` only creates the partial indexes, so an install upgraded from an older schema can retain the old key). Post-migration the same flow still fails — with `licenses_install_unique` in the message instead.
6. Secondary duplicate risk on the same theme: `installation-package.functions.ts:97-120` does check-then-`insert` on `license_installs` (which has a hard `license_installs_install_id_key`), so two concurrent package generations for one install can raise the same class of error.
7. Redundant duplicate indexes exist in cloud (`licenses_install_unique` + `licenses_one_install_per_id`, `licenses_module_unique` + `licenses_one_module_per_install`) — harmless but doubles write cost and makes error messages non-deterministic.

**Recommended fix (not applied):** give `issueLicense` the same existence guard as `issueModuleLicense` (or `upsert … onConflict:'install_id'` scoped to `kind='install'`), map unique-violation codes (`23505`) to a human message ("An install licence already exists for this install ID — use Re-issue"), add an install_id availability check in `IssueLicenseDialog` before submit, make `license_installs` writes true upserts, and drop the duplicated indexes.

## Findings
**P0**
- `issueLicense` unguarded insert → hard failure on every re-issue/collision, no UI recovery path (`licenses.functions.ts:93-136`).
- Raw Postgres error strings surfaced to users across nearly all MC mutations (`licenses.functions.ts:55,134,198,213,249,267`; `management.licenses.tsx:105`) — unreadable UX plus schema/constraint disclosure into client logs.

**P1**
- No pagination anywhere: `listLicenses`, `listCustomerProfiles`, `listInstallations`, `listReleases`, `listPlatformAuditLog` (capped `limit` only, max 500) fetch full sets and filter client-side.
- Inconsistent confirmations: native `confirm()` on revoke/delete/demote, **zero** confirmation on customer suspend (`management.customers.tsx:277-290`), promote-to-platform_admin (`management.ownership.tsx:313-361`) and "set release current" (`management.releases.tsx:176-185`) — the last flips the update target for every install on that channel.
- Slug-derived `install_id` suggestion can silently collide, feeding the P0.
- `license_installs` check-then-insert race (`installation-package.functions.ts:97-120`).

**P2**
- No un-revoke/reactivate action in the Licenses UI despite `revoked:false` being supported.
- New-customer dialog provisions a real admin password with client-side length check only (`management.customers.tsx:402-406`); no generator, no strength/breach guidance.
- Filter state not URL-persisted except `install` on Licenses (`:49`).
- Promote-by-typed-email has no user typeahead, unlike the company combobox in Issue License.
- `license_releases.version` is globally `UNIQUE` (introspected) while the UI models version per channel — publishing `1.2.0` on `beta` then `stable` is impossible and will surface as another raw duplicate-key toast.

**P3**
- Inline contract-status `Select` has no per-cell pending state (`management.customers.tsx:237-260`) — rapid changes can race.
- `management.portal.tsx` is dead code (unconditional redirect); `management.companies.tsx` likewise redirects to Customers (intentional alias).
- `onClick` on non-interactive `<div>` (`management.customers.tsx:238,276`).
- Fixed-px filter widths (`management.licenses.tsx:284,294,306`; `management.installations.tsx:187,197`; `management.customers.tsx:248,321,331,343`) risk overflow at 320-375px.
- Self-Hosted preview links mixed into the MC sidebar (`mc-shell.tsx:70-87`) blur product boundaries.

## Scores — Visual 8 / UX 7 / Functional 6 / Responsive 6 / Architecture 8 / Maturity 7

# REPORT 2 — CUSTOMER PORTAL

## Strengths
- Server-side ownership enforcement on every download: licence/bundle/module access is re-verified against the caller's **verified JWT email**, never client input (`portal.functions.ts:108-161`; `installation-package.functions.ts:227-268`), and every signed-URL mint is audit-logged with `actor_role:"customer"`.
- Staff/customer separation is enforced twice: client redirect (`portal.admin.tsx:6-21`, `management.tsx:8-24`) and `assertStaff` inside every mutating admin fn (`portal-admin.functions.ts:12-26`).
- Support is company-isolated by RLS (`20260627125401_*.sql:37-115`) with `requirePermission` on list/get/create/post.
- Sign-out clears the query cache (`portal.tsx:62-67`) — no cross-account cache bleed on shared devices.
- Clear licence-state modelling in the UI (Active/Suspended/Revoked/Pending, disabled buttons for revoked: `portal.downloads.tsx:110,179`), consistent `EmptyState` usage, mobile off-canvas nav.

## Findings
**P1**
- **Release Notes and Documentation are dead for real customers.** `listPortalReleases` (`portal.functions.ts:83-100`) and `listPortalDocs`/`getPortalDoc` (`:164-195`) use the *user-scoped* client, but `license_releases` RLS is `FOR ALL … has_role(auth.uid(),'platform_admin')` (`20260708191748_*.sql:99-103`) and `system_doc_catalog` policy is `is_platform_admin()` only (`20260630192245_*.sql:106-116`). Customers always see "No releases published yet" / "No documentation available" — a misleading empty state, not an access error. Sibling News works because `portal_announcements` has a customer-read policy (`20260716092452_*.sql:22-29`), so this reads as an RLS oversight.
- No unauthorized-state UI: pages rely on server rejection with no rendered 403 state.

**P2**
- `markSupportRead` (`support.functions.ts:171-183`) is the only support fn with no `requirePermission`/role gate; relies solely on RLS scope.
- Role-model inconsistency: `licenses`/`license_installs`/`license_orders`/`license_releases` RLS checks `platform_admin` only, while app `STAFF_ROLES`/route guards treat `platform_owner` as equal (`portal-admin.functions.ts:10`, `management.tsx:20-22`) — an owner-only account is denied licence data the UI offers.
- `getSupportConversation` trusts RLS with no app-level ownership check, inconsistent with the defence-in-depth used in `portal.functions.ts`.
- Two staff admin shells: portal content is managed from `/portal/admin/*` rather than `/management/*` — IA duplication of the "admin surface" concept.

**P3**
- Tenant binding is a **soft binding by `contact_email` string match** with no `company_id` FK — explicitly flagged as interim in code (`portal.functions.ts:6-9`). It is the single point of failure for portal tenant isolation; an email typo/reuse cross-links installs to the wrong customer.
- `bg-black/60` scrim (`portal.tsx:136`) is the only hardcoded colour in the app and diverges from the `bg-foreground/40` scrim used by the support widget.
- Portal mobile-nav scrim/drawer (`z-40`/`z-50`) shares z-values with the global support widget (`support-widget.tsx:379,400,406`) — stacking conflict when both open.
- `alt=""` on meaningful news covers/hero (`portal.admin.index.tsx:189`, `portal.news.tsx:72`, `portal.news.$slug.tsx:81`).
- Bare "Loading…" text (`portal.support.tsx:219`) vs skeletons elsewhere.
- Storage policies for `portal-news-images` / `portal-download-modules` were not locatable — verify customers cannot sign arbitrary paths (`portal-admin.functions.ts:272-289`).

## Scores — Visual 8 / UX 7 / Functional 6 / Responsive 7 / Architecture 6 / Maturity 6

# REPORT 3 — SELF-HOSTED APPLICATION

## Strengths
- Single AI chokepoint (`src/lib/ai-provider.server.ts`) plus a real Ollama adapter whose probe does live `/api/tags`, chat and embedding round-trips with per-step pass/fail (`ollama.ts:136-240`); `getAiEngineStatus` (`ai-engine.functions.ts:28-46`) is genuinely accurate.
- RAG citation UX is above market: primary/supporting docs, relevance %, confidence buckets, matched excerpt, "Open document" (`app.chat.$threadId.tsx:354-539`).
- Knowledge-gap handling: banner + escalation CTA (`:294-302,641-694`) and a hard refusal instruction when nothing is retrieved (`api/chat.ts:10,15`).
- Document versioning/rollback/critical-flag with history dialog (`app.knowledge.tsx:633-743`) exceeds typical KB tooling.
- Honest deployment-mode branching: "Create user with temp password" vs "Invite user" (`app.users.tsx:64,81-83,204-249`); unavailable composer affordances are visibly disabled rather than fake (`app.chat.index.tsx:105-110`).
- Status badges are DB-truthful and polled every 5s (`app.knowledge.tsx:157-161,750-773`).

## Findings
**P0**
- **Organization → AI provider tab misrepresents the architecture.** `app.organization.tsx:36-42,68-74,340-410` offers Lovable Gateway / OpenAI / Azure / Anthropic / Ollama plus free-text model + base URL, saves via `savePlatformAiConfig` (`mc-admin.functions.ts:80-107`) and shows "AI provider updated" — but the runtime adapter is selected solely from `process.env.AI_PROVIDER`, defaulting to `ollama` in selfhost (`ai-adapters/registry.ts:57-82`) and never reads that persisted config. Admins get false confidence they switched engines, contradicting the Global Self-Hosted AI Contract (`ai-provider.server.ts:1-10`), and the base-URL field implies outbound calls on an air-gapped install. The real Ollama-scoped config path (`ai-engine.functions.ts:50-80`, re-probes embedding dim + realigns pgvector) is only reachable from the Management Center.
- **No AI-unavailable / stream-error state in chat.** `onError` is `console.error` only and `status` is used solely for `loading` (`app.chat.$threadId.tsx:182,185`); `api/chat.ts:18-76` has no top-level try/catch. With Ollama down the user sees an eternal thinking state or silently truncated output — no error, no retry.

**P1**
- No unauthorized UI for permission-gated pages (e.g. `/app/users` renders actions for everyone and depends on server rejection; `list.isError` unhandled).
- Organization AI tab visible to company `isAdmin` while the server requires `requirePlatformAdmin` — guaranteed failing submit for that role.
- No engine-health surface inside the app shell: nothing in `app.tsx`/`app-shell.tsx` tells a company admin that Ollama/Postgres/pgvector/Caddy is down; `app.audit.tsx` is KB-coverage only.

**P2**
- FAQ edit is `isAdmin` only while Knowledge is `isAdmin || isManager`, despite overlapping content roles.
- FAQ is DE/EN only (`app.faq.tsx:215,220`) while chat detects RO (`api/chat.ts:11-13`).
- No duplicate-document detection on upload (no hash/title check) — same file twice creates two indexed documents.
- Raw `d.error` strings from processing shown verbatim in failed-document cards (`app.knowledge.tsx:567-572`) — possible internal-detail leak.
- FAQ keyword-matched sources and vector-matched chunks are merged into one `sources` array and one confidence value with mismatched semantics (`api/chat.ts:51-58`).
- No server-side guard that a zero-source answer actually contains the refusal — a chatty local model can still hallucinate.

**P3**
- `ChatSidebar` is `hidden lg:flex` (`chat-sidebar.tsx:146`) — no in-page thread-history affordance below `lg`.
- Client-side-only search for Knowledge (`:309-320`) and FAQ (`:119-128`); no server-side/vector search, no pagination/virtualization for threads.
- 5s polling latency for document status; deletes use native `confirm()` with no undo (`:209-217`).
- Feedback bar failures are silent (`app.chat.$threadId.tsx:541-570`).
- No explicit code-block/table styling for markdown output; `grid-cols-5` without breakpoints (`app.academy.analytics.tsx:248`), `grid-cols-3` (`app.audit.tsx:209`).

# CROSS-PRODUCT REPORT

## Visual consistency
Token layer is genuinely consistent — all three shells consume the same `src/styles.css` variables (emerald / parchment / gold, `--radius: 0.875rem`, `--shadow-xs..lg`); only **one** hardcoded colour exists in the entire app surface (`portal.tsx:136`). Divergence is in utilities layered on top:
- Radius: 5 competing variants in use (`rounded-full` ×57, `rounded-lg` ×37, `rounded-md` ×33, `rounded-2xl` ×15, `rounded-xl` ×4) with no canonical card radius.
- Shadows: only 20 uses across 71 files, 6 variants, plus a marketing-only `--oix-shadow-gold-glow` outside the shared scale.
- `font-display` (Space Grotesk) is applied consistently in MC/marketing headers but sparsely in Portal headers.
- `StatusBadge` re-implemented twice (`first-run.tsx:743`, `app.knowledge.tsx:750`) instead of using shared `ui/badge`/`ui/stat-card`.

## Navigation consistency
- Two staff admin shells (`/management/*` and `/portal/admin/*`) for the same audience — the main IA defect.
- Dead/alias routes: `management.portal.tsx`, `management.companies.tsx` (both pure redirects). No unregistered route files (all 47 in `routeTree.gen.ts`).
- Terminology drift: "Customers" (MC) vs "Companies" (schema/detail route) vs "Organization" (self-hosted) for overlapping concepts; "Subscription" exists in both Portal and self-hosted app with different meaning (hidden in selfhost mode).
- Engine health lives only in MC Settings while the audience that needs it is the self-hosted admin.

## Duplicated functionality (intentional vs not)
- Intentional and correctly isolated: installer-package download (customer self-service vs staff-operated), release management (MC writes, Portal reads), support (single shared backend, `scope: mine|platform`).
- Not intentional: portal content CRUD living outside MC; duplicated `StatusBadge`; duplicated partial unique indexes on `licenses`.

## Missing functionality
Un-revoke in MC; pagination everywhere; customer-visible releases/docs (RLS); in-app engine-health banner; duplicate-document detection; unauthorized-state components; per-channel release versioning.

## Role boundary problems
- Portal tenant identity is an email string, not a tenant FK.
- `platform_owner` is app-privileged but RLS-blind on four licence tables.
- Self-hosted Organization page exposes a platform-admin-only AI form to company admins.
- MC sidebar links into the self-hosted product view.

## Responsive
- Tables are safe (`ui/table.tsx:7` wraps in `overflow-auto`); single correct `<main>` per shell (MC/Portal/App).
- **16 `h-screen`/`min-h-screen`, zero `h-dvh`** — iOS viewport risk, worst in chat and academy lesson surfaces.
- 18 fixed-px widths in MC/Knowledge filter toolbars with no responsive variants → 320-375px overflow.
- Portal drawer vs support-widget z-index collision.

## Accessibility
~20 of 22 icon-only buttons lack `aria-label` (`title` only): `app.chat.index.tsx:105,108,115`, `management.team.tsx:325,904`, `management.support.tsx:288,402`, `app.chat.$threadId.tsx:340`, `support-widget.tsx:422,462`. 5 of 6 `<img>` use `alt=""` including meaningful covers/avatars. 2 `onClick` on `<div>`. 90 `<Input>` instances need a label-association sweep. No `h-dvh` adoption.

## Performance / code quality
`public/favicon.png` is **1.0 MB**; `src/assets/empty-installations.png` 520 KB, `empty-knowledge.png` 178 KB, `empty-team.png` 164 KB, `empty-chat.png` 149 KB, `marketing-hero.jpg` 249 KB — PNG used for illustrative art that should be SVG/WebP. No duplicated hooks; no dead routes.

# IMPLEMENTATION ROADMAP

**PHASE 1 — P0/P1 functional** (MC + Self-Hosted + Portal, HIGH, no deps)
`issueLicense` idempotency + 23505 error mapping + install_id availability check; `license_installs` upsert; drop duplicate indexes; chat error/retry state + `api/chat.ts` try/catch; reconcile Organization AI tab with the Ollama-only contract; customer-read RLS for `license_releases`/`system_doc_catalog`; `requirePermission` on `markSupportRead`; `platform_owner` added to licence-table RLS. Impact: removes every known blocker and two silent-failure classes.

**PHASE 2 — Information architecture & navigation** (all areas, MEDIUM, after 1)
Merge `/portal/admin/*` into `/management/*`; remove alias/dead routes; unify Customers/Companies/Organization terminology; move engine health into the self-hosted shell; separate self-hosted preview links in MC sidebar.

**PHASE 3 — Shared design-system consistency** (all, MEDIUM, after 2)
Canonical radius/shadow scale; one shared `StatusBadge`/status-pill; single scrim token + z-index scale; consistent `font-display` header rule.

**PHASE 4 — Management Center polish** (MC, MEDIUM, after 1+3)
Server-side pagination/sorting; themed AlertDialog confirmations incl. suspend/promote/set-current; un-revoke action; URL-persisted filters; user typeahead for promote; per-channel release versioning; password generator.

**PHASE 5 — Customer Portal polish** (Portal, MEDIUM, after 1+2)
Tenant binding by `company_id` instead of email; skeleton loaders; real `alt` text; verify storage-path signing; distinguish "empty" from "not permitted".

**PHASE 6 — Self-Hosted polish** (Self-Hosted, HIGH, after 1)
Engine-health banner; unauthorized-state component; duplicate-document detection; sanitized processing errors; separate FAQ vs vector confidence semantics; align FAQ/Knowledge permissions and language coverage; server-side refusal validation.

**PHASE 7 — Mobile / responsive** (all, MEDIUM, after 3)
`h-screen`→`h-dvh` (16 sites); responsive filter toolbars (18 fixed widths); breakpoint fallbacks for `grid-cols-5/3`; mobile thread-history affordance; drawer vs support-widget stacking.

**PHASE 8 — Accessibility** (all, LOW-MEDIUM, after 3)
`aria-label` on ~20 icon buttons; label association sweep over 90 inputs; keyboardable interactive elements; focus-visible audit; 44px touch targets.

**PHASE 9 — Final UX polish** (all, LOW, after 4-8)
Asset optimisation (1 MB favicon, 150-520 KB empty-state PNGs → SVG/WebP); loading-state consistency; markdown table/code styling; feedback/undo affordances.

**PHASE 10 — Regression QA** (all, MEDIUM, after 9)
Licence lifecycle matrix (issue/re-issue/revoke/un-revoke/module/transfer); portal read-path per role; Ollama-down and Postgres-down chat/KB behaviour; 320/375/390/430/tablet/desktop × light/dark sweep.
